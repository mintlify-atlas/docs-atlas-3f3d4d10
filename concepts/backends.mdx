Notify is designed around native OS APIs. On each platform, it selects the most capable available backend and exposes it through the uniform `Watcher` trait. The type alias `RecommendedWatcher` always resolves to the best choice for the current target, so most code never needs to name a concrete backend.

## Backend Selection by Platform

| Platform | Backend type | Cargo feature |
|---|---|---|
| Linux, Android | `INotifyWatcher` | Enabled by default |
| macOS | `FsEventWatcher` | `macos_fsevent` (default) |
| macOS (opt-in) | `KqueueWatcher` | `macos_kqueue` |
| Windows | `ReadDirectoryChangesWatcher` | Enabled by default |
| FreeBSD 14.5+ (native build) | `INotifyWatcher` | Automatic |
| FreeBSD 14.5+ (cross-compile) | `INotifyWatcher` | `freebsd_inotify` |
| FreeBSD (older), OpenBSD, NetBSD, DragonflyBSD, iOS | `KqueueWatcher` | Enabled by default |
| All platforms | `PollWatcher` | Always available |

`RecommendedWatcher` is a type alias; it compiles to whichever backend is appropriate for the target. The free function `notify::recommended_watcher(handler)` constructs it with `Config::default()`.

You can check at runtime which backend was selected using the static `Watcher::kind()` method:

```rust
use notify::{RecommendedWatcher, Watcher, WatcherKind};

match RecommendedWatcher::kind() {
    WatcherKind::Inotify                  => println!("using inotify"),
    WatcherKind::Fsevent                  => println!("using FSEvents"),
    WatcherKind::Kqueue                   => println!("using kqueue"),
    WatcherKind::ReadDirectoryChangesWatcher => println!("using ReadDirectoryChangesW"),
    WatcherKind::PollWatcher              => println!("using polling"),
    WatcherKind::NullWatcher              => println!("using null watcher"),
    _ => {}
}
```

## INotifyWatcher — Linux, Android, FreeBSD 14.5+

The inotify backend is a thin Rust wrapper around the Linux kernel's `inotify` subsystem. Each watched path consumes one inotify watch descriptor; watching a directory recursively allocates one descriptor per file and subdirectory inside it.

**Strengths:**
- Kernel-level notification — no polling overhead.
- Supports kernel-level event filtering when you pass a non-`ALL` `EventKindMask`. Unneeded event categories are masked at the kernel boundary, not just in userspace.

**Limitations and caveats:**
- The default system limit on inotify watches is low (often 8 192). On systems where users watch large trees, this limit is commonly hit. The error surfaces as `ErrorKind::MaxFilesWatch` or a generic I/O error. Increase the limit with:

  ```sh
  sudo sysctl fs.inotify.max_user_watches=524288
  sudo sysctl fs.inotify.max_user_instances=8192
  sudo sysctl -p
  ```

- Inotify is documented as not 100% reliable under very high event rates; see [issue #412](https://github.com/notify-rs/notify/issues/412).
- Network mounts (NFS, CIFS) and pseudo-filesystems (`/proc`, `/sys`) do not emit inotify events. Use `PollWatcher` with `with_compare_contents(true)` for those.

**FreeBSD note:** Native FreeBSD builds on 14.5+ automatically use inotify. Cross-compilation to FreeBSD 14.5+ requires the `freebsd_inotify` Cargo feature to opt in explicitly.

## FsEventWatcher — macOS

The FSEvents backend calls Apple's `FSEvents` API. It delivers events asynchronously via a callback thread, and the first event in an idle period arrives immediately (notify sets `kFSEventStreamCreateFlagNoDefer`). Subsequent events within the configured `fsevent_latency` window are coalesced before delivery.

**Strengths:**
- Low overhead; events are generated by the kernel and delivered via a background thread.
- Works across volumes and network mounts that the OS surfaces through FSEvents.

**Limitations and caveats:**

<Warning>
  Due to the FSEvents security model, some events may not be observable for files
  you do not own. If you encounter missing events for unowned files, switch to
  `PollWatcher` as a fallback. See
  [FileSystemEventSecurity](https://developer.apple.com/library/mac/documentation/Darwin/Conceptual/FSEvents_ProgGuide/FileSystemEventSecurity/FileSystemEventSecurity.html).
</Warning>

- `std::fs::copy` on APFS may use copy-on-write cloning (`clonefile`), which updates inode metadata on the *source* file. FSEvents then reports a metadata-change event for the source path even though its content was not modified. Filter out `EventKindMask::MODIFY_META` if spurious metadata events are a problem.
- Adding many independent paths via separate `watch()` calls causes O(N²) stream rebuilds because FSEvents rebuilds the underlying stream each time a new path is not already covered by a recursive watch on the same volume.

<Tip>
  On macOS, always use `Watcher::update_paths()` when registering more than a
  handful of independent paths. A single `update_paths` call rebuilds the
  FSEvents stream exactly once for the entire batch.
</Tip>

Configure the coalescing window with `Config::with_fsevent_latency`:

```rust
use notify::{Config, RecommendedWatcher, RecursiveMode, Watcher};
use std::{path::Path, time::Duration};

let config = Config::default()
    .with_fsevent_latency(Duration::from_millis(100));

let mut watcher = RecommendedWatcher::new(|res| println!("{res:?}"), config)?;
watcher.watch(Path::new("/Users/alice/projects"), RecursiveMode::Recursive)?;
```

## KqueueWatcher — BSD, iOS, optional macOS

The kqueue backend uses the BSD kernel event notification interface. It is the default on FreeBSD (pre-14.5), OpenBSD, NetBSD, DragonflyBSD, and iOS. On macOS it is available as an opt-in via the `macos_kqueue` Cargo feature (which disables `FsEventWatcher`).

**Strengths:**
- Works on all BSD variants and iOS.
- Supports `with_follow_symlinks` via `WatchPathConfig::with_dereference_symlinks`.

**Limitations:**
- Like inotify, watching large recursive trees allocates one kernel object per file descriptor; the OS limit on open file descriptors applies.
- Event granularity is generally coarser than inotify; some subkind information may be reported as `Any`.

## ReadDirectoryChangesWatcher — Windows

The Windows backend wraps the `ReadDirectoryChangesW` API. It delivers events for files and directories within a watched subtree using kernel-mode callbacks.

**Path separator style:** By default (`WindowsPathSeparatorStyle::Auto`), the separator in emitted event paths mirrors the separator in the watched input path — watching `C:/tmp` yields forward-slash paths, watching `C:\tmp` yields backslash paths. Override this with `Config::with_windows_path_separator_style`:

```rust
use notify::{Config, WindowsPathSeparatorStyle};

// Always emit forward-slash paths regardless of input style
let config = Config::default()
    .with_windows_path_separator_style(WindowsPathSeparatorStyle::Slash);
```

## PollWatcher — Universal Fallback

`PollWatcher` is implemented entirely in Rust using `std` APIs. It works on every platform notify supports, and it is the only backend that works correctly on:

- Network-mounted filesystems (NFS, CIFS, SMB)
- Linux pseudo-filesystems (`/proc`, `/sys`)
- Docker containers on macOS M1 where the native backend throws `ENOSYS`

`PollWatcher` periodically walks the watched paths, compares modification timestamps (and optionally file content hashes), and emits synthetic events for anything that changed.

### Automatic polling

By default, `PollWatcher` scans every 30 seconds. Tune the interval with `Config::with_poll_interval`:

```rust
use notify::{Config, PollWatcher, RecursiveMode, Watcher};
use std::{path::Path, time::Duration};

let config = Config::default()
    .with_poll_interval(Duration::from_secs(2))
    .with_compare_contents(true); // needed for /proc, /sys

let mut watcher = PollWatcher::new(|res| println!("{res:?}"), config)?;
watcher.watch(Path::new("/proc/self/status"), RecursiveMode::NonRecursive)?;
```

### Manual polling

Disable automatic scanning and drive polls yourself:

```rust
use notify::{Config, PollWatcher, RecursiveMode, Watcher};
use std::path::Path;

let config = Config::default().with_manual_polling();
let mut watcher = PollWatcher::new(|res| println!("{res:?}"), config)?;
watcher.watch(Path::new("/data"), RecursiveMode::Recursive)?;

// Trigger a scan whenever you want
watcher.poll()?;

// Or block until the scan cycle completes
watcher.poll_blocking()?;
```

`poll()` sends the scan request and returns immediately; `poll_blocking()` waits for the scan thread to finish the full cycle before returning. Manual polling is ideal for test suites that need deterministic timing.

## Choosing a Backend at Runtime

A common pattern is to fall back to `PollWatcher` when the recommended backend is not suitable:

```rust
use notify::{Config, PollWatcher, RecommendedWatcher, RecursiveMode, Watcher, WatcherKind};
use std::{path::Path, time::Duration};

fn main() -> notify::Result<()> {
    let (tx, rx) = std::sync::mpsc::channel();

    let mut watcher: Box<dyn Watcher> = if RecommendedWatcher::kind() == WatcherKind::PollWatcher {
        // Custom config for PollWatcher
        let config = Config::default()
            .with_poll_interval(Duration::from_secs(1));
        Box::new(PollWatcher::new(tx, config)?)
    } else {
        // Default config for all native backends
        Box::new(RecommendedWatcher::new(tx, Config::default())?)
    };

    watcher.watch(Path::new("."), RecursiveMode::Recursive)?;

    for e in rx {
        println!("{e:?}");
    }

    Ok(())
}
```
